# VirtualWorld 技术底座审查与优化

审查日期：2026-10-19。基线为 `e610e685999ea4766657e50f4d5fedd37bbce9a7`，优化分支为 `feat/platform-foundation-20261019`。审查依据是实际源码、固定版本依赖、回归测试和生产构建；第三方库文档仅用于解释能力边界。此前 PR #5 的入口加载优化和 PR #6 的 WebGL 恢复已在基线内，不重复计为本次新增。

## 结论

项目有可继续演进的技术底座：声明式 SceneSpec、原子 SceneCommands、编辑器与播放器共享的运行时、资产来源与运行版本分离、实际浏览器物理和剧情、持久生成账本都有实现和测试。继续保留 React / Three / Rapier / Fastify 的模块化单体合理，现阶段没有必要为了上线而整体换引擎或拆成大量服务。

仓库**已经有 Fastify 后端**，并非只有网页前端。原先更接近本地创作工作室，缺的是远程使用所需的访问控制、持久部署边界、容量限制和明确的多用户语义。本次补齐了一套私有团队共享工作区的基础，并修复模型导入、发布和导出中的可复现问题。

它仍不是公有多租户 SaaS、实时协同编辑器或多人联机游戏服务器。多人同时打开页面、多人编辑同一项目、多人在同一世界共享角色状态是三种不同的需求，不能用同一项“多人支持”概括。部署配置和功能测试也不等于完成真实容器、域名、GPU 或线上容量验收。

### 本次修复的导入保真问题

原来的分解方式适合静态正尺度 CAD 零件，却可能把骨骼模型拆散，丢失动画根节点、负尺度、原始可见性或非 Mesh 对象。当前根据实际层级选择表示方式：静态普通 Mesh 保留逐部件编辑；含骨骼、动画、镜像或其他不能无损表示的对象时，保留整个 GLB 根节点，用单位变换的 SceneSpec 节点包裹。

导入保留 GLTFLoader 返回的动画元数据，首个名称符合现有协议的片段可循环播放；没有新增骨骼编辑器、轨道编辑或多片段选择界面。复杂资产因此可能作为整体编辑，这是保留原始内容所作的明确取舍。实例独立克隆骨骼、材质和纹理；整根导入中的 Line / Points 也分配自己的几何与材质，避免删除一个实例影响另一个。

上传前现统一运行自包含检查和 Khronos 校验，失败时不会先留下原件或 manifest。一个额外兼容性陷阱是：Validator 对未知扩展可能只给信息，即使它出现在 `extensionsRequired`。本次加入与固定 Three r180 默认 Loader 对齐的 18 项必需扩展白名单；未知必需扩展拒绝，未知可选扩展保留信息。升级 Three 时必须重新核对该集合。

复审还发现 Draco 仅出现在 `extensionsUsed` 时，固定 Loader 也会立即要求 DRACOLoader。因此该声明同样在发布前拒绝，避免“服务器接受、浏览器和离线播放器都打不开”；BasisU/Meshopt 的可选声明及普通未知可选扩展保留现有回退规则。对应回归使用相同真实三角 GLB 先验证实际 Loader 行为。

验证不是只用伪造文件头：回归包含仓库内真实带骨骼/动画的 GLB、两个独立实例、原始显隐/镜像/非 Mesh 层级、未知扩展、真实三角网格和已运行的 `KHR_materials_unlit` Loader 处理器。见[导入保真回归](../tests/assets/import-fidelity.test.ts)。

## 2. 浏览器渲染与游戏运行时

Three WebGL2 是当前实际图形后端，Rapier 提供探索模式的物理，Spark 处理 Splat。React 管理界面，场景对象、动画循环、选择、变换、截图和资源由共享 runtime 管理；编辑器、普通体验和导出播放器使用同一套引擎。浏览器承担本地绘制和单人模拟，不是服务器传回实时渲染视频。

已有能力包括第三人称行走、静态碰撞、球面导航、角色 GLB 动画、任务与对话、分章进度、工业部件观察，以及 WebGL 初始化失败/上下文丢失/恢复的持久提示。SceneSpec 与浏览器试玩进度分开保存，是有价值的边界；也有重复更新资源检查、端口隔离的导出检查和真实浏览器测试。

需要纠正一个此前文档表述：`Viewport` **已经保留 runtime 和 renderer**。剩余问题在 `loadScene` 仍清理并重建场景内容及当前缓存，编辑一个属性也可能触发大范围加载/编译/物理重建。下一步应按 SceneCommands 对节点和资源做增量更新，用取消代次与引用所有权控制异步内容；先测量编辑频率、加载次数、draw calls、显存对象和最慢设备，再决定缓存上限与实例化策略。

本应用还没有启用大世界分区流式加载或 Splat LOD：代码明确设置 `lod:false` 和 `enableDriveLod:false`。Spark 官方有 LOD 能力，接入仍需资产预处理、交付格式、视距策略和设备预算；不能把依赖项能力直接算成本项目能力。当前也没有 WebGPU 后端、完整 NavMesh、通用游戏脚本系统或网络复制。

资源释放仍需继续审查 ImageBitmap 的关闭所有权、InstancedMesh 的特有 GPU 释放和继承可见性的碰撞语义。已有功能测试不能证明无限时长无泄漏，也不能证明移动设备或真实驱动稳定。代码证据：[Viewport](../apps/web/src/Viewport.tsx)、[runtime](../packages/engine/src/runtime.ts)、[AssetRegistry](../packages/asset-runtime/src/registry.ts)。官方资料：[WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html)、[Spark LOD](https://sparkjs.dev/docs/lod-getting-started/)。

独立审查将两项既有问题保留为非阻塞后续项：InstancedMesh 释放缺少对象专有 dispose 事件（已复现事件缺失，未测量 GPU 泄漏速率）；静态隐藏叶节点在导入 helper 与 registry 中可能受到双层显隐控制，导致外层取消隐藏仍不可见。后一项只在人工构造的 helper 输入复现，当前固定 GLTFLoader/CAD 入口不产生这种隐藏叶节点，不能描述成普通用户 GLB 导入必现故障。

## 3. AI 生成：流程有基础，质量与执行边界要分开

实际管线是描述/参考图 → LLM 生成声明式规划 → 验证 SceneSpec → 程序化资产或显式选择 Tripo → 保留原始资产 → glTF Transform 优化与 Validator → 发布世界三文档。编辑时 LLM 生成的是有限 SceneCommands，校验后才可应用，不会直接 eval JavaScript。

已有服务端密钥、请求身份、Provider/模型快照、输入输出哈希、任务账本和恢复逻辑。Tripo 付费创建前持久化 `creating`，创建 POST 不自动重试；未知结果需要核实原 task ID 后显式恢复。这比无状态地反复调用生成 API 更适合继续演进。`builtin` 明确表示不调用模型的确定性程序化模式，不理解参考图。

本次把活跃和排队生成任务总数限制为默认 8。饱和时拒绝新任务并返回 429，已接受请求仍能幂等重放；关闭后拒绝新作业，恢复路径也受同一容量限制。交互 AI 独立限制为并发 2。两者保护不同的工作，不能把任务队列长度误当成用户配额或付费预算。

目前未做真实付费供应商测试，也没有自动评价“生成世界可玩性”、镜头/碰撞/关卡难度或视觉质量。合法 JSON/GLB 只证明协议层面可接受。模型处理与导出仍在同一 Node 服务内协调；ZIP 压缩已异步，部分几何/结构处理和大场景校验仍可能消耗进程资源。面对不受信任的上传或更重负载时，应隔离 worker，增加任务超时、进度、可取消处理、磁盘保留、租户配额和可观测性。

代码证据：[planner](../generators/planner/src/index.ts)、[完整世界规划](../generators/planner/src/world.ts)、[GenerationService](../apps/web/server/generation.ts)、[Tripo](../generators/tripo/src)、[优化流水线](../generators/scene-builder/src/pipeline.ts)。

## 4. 是否需要专门后端，以及“多人”如何定义

| 目标                            | 所需部署                                                      | 当前覆盖                                                                                         |
| ------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 多个访客各自浏览已发布世界      | 静态 HTTP/CDN 托管导出产物                                    | 已支持；浏览器各自维护单人状态，访问数量主要受静态交付和客户端设备约束。无需创作 API。           |
| 在网页保存、上传、AI 创建与导出 | Fastify 应用后端 + 持久存储 + 访问控制                        | 后端已存在，本次补齐私有托管、容量和持久路径；不要把包含服务端密钥的功能做成纯前端。             |
| 多位可信成员共享一个工作区      | 一个应用实例 + TLS 认证网关 + 一个工作区卷                    | 本次提供配置及接口回归。所有成员看到同样的项目和资产；同修订同时保存只有一个成功，其他收到 409。 |
| 多租户商业 SaaS                 | 用户认证、项目级 ACL、数据库、对象存储、任务隔离与配额        | 未实现。单个共享密码头不承载用户身份，JSON 单实例也不能直接横向扩容。                            |
| 同一项目多人实时编辑            | 操作订阅、连接状态、操作排序与冲突合并策略                    | 未实现。当前乐观修订检查避免静默覆盖，不会合并同时编辑。                                         |
| 同一世界多人实时联机            | 独立房间/会话服务、服务器权威状态、输入与快照复制、插值及重连 | 未实现。现有 Rapier、localStorage 存档和剧情状态属于单客户端；仅添加 WebSocket 不能完成联机。    |

**建议保留现有后端并明确部署职责。** 浏览器完成渲染与本地交互；后端管理内容、权限、密钥、任务和发布；独立静态播放器承担公开浏览。达到多租户或长任务负载阶段时，将已有模块移动到 worker/存储服务，保留 SceneSpec 和资产协议，不需要先重写 Three 前端。

### 本次加入的共享工作区保护

- `local` 默认回环绑定，并检查 Host/Origin；未配置数据目录时保留已有本地存储布局。
- `hosted` 要求明确 HTTPS origin、持久数据目录和独立随机网关秘密。所有应用/资产/API 路由都需网关认证，包含没有 Origin 的请求；仅内部最小健康端点例外。
- Caddy 对全部应用路径做账号认证，经 TLS 传递浏览器凭据；覆盖内部网关头，移除 Authorization 与常见身份头。后端没有公开端口，不把转发用户名当作授权。
- 一个数据目录只允许一个服务持有租约。先获得租约再做生成恢复，第二个实例不能先把在跑任务改成中断。崩溃残留租约由运营者核实后处理。
- 项目/生成/参考图/上传与生成资产进入持久数据路径；只读内置世界和新生成世界都可列出、读取、校验和导出。
- JSON/图片/模型分别限 2/20/100 MiB；导出默认并发 1、逻辑未压缩内容 256 MiB，包含章节、元数据和许可证。ZIP 用异步压缩，客户端在预检或压缩中断开都会触发取消；结果仍组装在内存中。
- 内部错误返回无敏感内容的 500 和请求 ID；输入错误保留可操作的 400，API 禁用共享缓存。系统没有添加每用户上传限流、磁盘配额或公网滥用防护承诺。

## 5. 游戏引擎支持与演进方向

Three + Rapier 足以继续做当前浏览器世界、轻量关卡和工业交互。项目已经封装部分引擎职责，仍需自己实现游戏工具链、场景增量更新、导航、联机和编辑协作；Three 本身不是完整商业游戏引擎。

GLB 提供的是**资产层互通**。Godot 官方支持 glTF 2.0，Unity 可使用 glTFast 读取 glTF；这并不自动迁移 SceneSpec 的互动条件、球面角色控制、机构语义、剧情进度或服务端状态。当前没有 Unity/Godot 项目导出器、运行时适配层或双向同步。若将来确需原生游戏项目，先定义 SceneSpec → 引擎场景/材质/动画/碰撞/交互的明确映射，并决定哪些特性无法转换，再实现单向适配器。

官方资料：[Godot 3D 格式](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)、[Unity glTFast](https://docs.unity3d.com/Packages/com.unity.cloud.gltfast@6.0/manual/index.html)。

## 6. 后续优先级与验收条件

| 顺序 | 工作                       | 触发与可验收结果                                                                                                                                  |
| ---- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 目标环境完成私有部署验收   | Docker 构建/非 root 卷权限、真实 TLS、未登录访问拒绝、备份恢复、异常退出与任务恢复；并以代表性世界测量内存和导出峰值。                            |
| 2    | 场景增量更新与资源所有权   | 连续编辑不重复重载未变化的 GLB；切换/删除/取消后 GPU 资源回到稳定区间；补齐特殊对象与解码图片释放。                                               |
| 3    | 更完整的资产接收与处理边界 | 实际有压缩模型、大 Splat 或外部 glTF 用户时，补结构验证、解码/LOD 产线、worker 隔离、容量与磁盘保留。                                             |
| 4    | 多租户数据层               | 需要用户隔离或多个 API 实例时，先引入 OIDC/项目 ACL、PostgreSQL 修订事务、对象存储及持久队列；迁移资产 URL/ID 保持兼容。                          |
| 5    | 实时协作或联机             | 先选择具体产品语义。编辑协作设计命令合并；联机设计房间权威状态、同步字段和预测/重连；分别有多人并发测试，不能共用一句“加 WebSocket”作为完成标准。 |

当前版本没有进行大规模并发压测、长期运行测试、真实手机 GPU、真实付费模型或公网部署。所有已执行检查及具体数量集中在[本分支验证记录](validation-platform-foundation.md)，该记录与测试源码一起作为交付证据。
